# verify

검증 전용 step. 이 step이 끝나면 **커밋해도 되는지**가 정해져 있다. 코드는 고치지 않고, 커밋하지 않는다.

## 원칙

- `${CLAUDE_PLUGIN_ROOT}/skills/RULES.md`를 읽고 따른다. 같은 대화에서 이미 읽었으면 건너뛴다.
- **실패해도 끝까지 검사한다.** 실패는 모아서 한 번에 보고한다. 앞 실패 때문에 실행할 수 없는 검사는 미수행으로 적고 이유를 붙인다.

## 실행

### 1. 변경된 코드 범위 읽기

`git status`와 `git diff HEAD`로 마지막 커밋 이후 바뀐 파일과 내용을 정리한다.

### 2. 코드 동작 확인 및 검증

1. **검증 명령어**
   - ticket 파일의 `기준 상태`에 적힌 검증 명령어를 전부 돌린다. 적힌 것이 없으면 저장소에서 찾은 검증 명령어를 돌린다.
   - 결과를 ticket 파일의 `기준 상태`와 비교한다. 원래부터 있던 실패는 "기존"으로 이름만 적고, **새로 생긴 실패**만 이번 변경의 실패로 본다.
2. **실제 동작 확인**
   - ticket 파일의 `기준 상태`에 적힌 실제 동작 확인 방법과 ticket 파일의 변경 계획에 적힌 검증 방법대로, 만든 것을 직접 실행해 확인한다. 무엇을 했고 무엇을 봤는지 모아 둔다.
   - 빌드 통과와 자기 판단은 증거로 치지 않는다.
   - 확인 과정을 스크립트로 만들 수 있으면 scratch 폴더에 만들어 돌린다.
   - 직접 확인할 수 없으면 이유와 사용자가 확인할 방법을 모아 둔다. "확인 못 함"은 통과가 아니다.
3. **검증 방법 준수**
   - spec.tmp.md나 debug.tmp.md에 정해진 테스트 지점이 있으면, 그 지점의 테스트가 이번 변경에 들어 있는지 본다.

### 3. 저장소 규칙·컨벤션 검토

저장소의 `CLAUDE.md`와 이번 작업에 해당하는 규칙·컨벤션 문서를 이번 diff에 맞대어 본다. 위반마다 `파일:줄`과 어긴 규칙을 적는다.

### 4. 요구사항과 설계

1. **문서 읽기**: 아래 문서를 우선순위에 맞게 모두 읽는다. 내용이 서로 다르면 우선순위가 위에 있는 것을 따른다. 하나도 없으면 "요구사항과 설계 문서 없음, 대조 안 함"으로 적고 넘어간다. 문서를 추측해서 만들지 않는다.
   - 입력으로 주어진 ticket 파일
   - scratch 폴더의 spec.tmp.md
   - scratch 폴더의 scope.tmp.md
   - scratch 폴더의 debug.tmp.md
2. **대조 하기**: 위 문서 읽기 내용과 변경된 코드를 대조한다. 대조는 `새 컨텍스트로 시작하는 subagent`에 맡기며, 읽은 문서 경로와 diff만 넘기고 아래와 같이 지시한다.
   - `문서 읽기`의 내용을 diff와 하나씩 맞대어 **빠진 것 / 범위를 넘은 것 / 다르게 만든 것**으로 분류한다.
   - 항목마다 근거로 문서의 해당 문장과 코드의 `파일:줄`을 둘 다 붙인다. 한쪽이 없으면 "없음"으로 적는다.
3. subagent의 결과는 고치거나 요약하지 않고 `기록 쓰기` 단계에 그대로 싣는다.

### 5. 결과 판정

위에서 찾은 모든 결과를 아래 기준으로 나눈다. `❌ 실패`가 하나라도 있으면 verify 결과는 실패, 없으면 통과다. `⚠️ 경고`는 `기록 쓰기` 단계에 남긴다.

- **❌ 실패**
  - `코드 동작 확인 및 검증`의 검증 명령어에서, ticket 파일 `기준 상태`에 없던 새 실패
  - `저장소 규칙·컨벤션 검토`에서 찾은 위반
- **⚠️ 경고**
  - `코드 동작 확인 및 검증`의 실제 동작 확인을 하지 못함
  - `코드 동작 확인 및 검증`의 검증 방법 준수에서, spec.tmp.md나 debug.tmp.md에 정해진 테스트가 빠짐
  - `요구사항과 설계`의 대조에서 다르게 만든 것, 범위를 넘은 것. 옳은 판단일 수 있어서 결정은 사용자 몫이다
  - `요구사항과 설계`의 대조에서 빠진 것. 종합에 따로 한 줄로 올려서 "통과"가 "다 만들었다"로 읽히지 않게 한다

### 6. 기록 쓰기

`tmp.md 기록 규칙`대로 ticket 파일에 verify 기록을 쓰고, 아래 결과를 덧붙인다.

```markdown
## verify 결과

<✅ 통과 | ❌ 실패>

### 변경된 코드 범위

<바뀐 파일 목록>

### 코드 동작 확인 및 검증

<검증 명령어 결과와 기준 상태 비교, 실제 동작 확인에서 한 일과 본 것, 정해진 테스트가 들어갔는지>

### 저장소 규칙·컨벤션 검토

<어긴 규칙마다 파일:줄과 규칙. 없으면 "없음">

### 요구사항과 설계

<subagent 결과 그대로>

### 종합

<실패 항목, 경고 항목. 빠진 것은 따로 한 줄로>

### 커밋 메시지 초안

<통과했을 때만. CLAUDE.md와 최근 커밋 메시지의 형식을 따른다>
```

### 7. 종료

verify 결과와 종합을 간결하고 이해하기 쉽게 보고하고 멈춘다.
