# spec

구현 명세 전용 step. 이 step이 끝나면 **어떻게 만들지**가 정해져 있다. 코드는 고치지 않는다.

## 원칙

- `${CLAUDE_PLUGIN_ROOT}/skills/RULES.md`를 읽고 따른다. 같은 대화에서 이미 읽었으면 건너뛴다.
- 기억, 대화 내용, ADR, scope.tmp.md는 힌트다.
- 지금의 코드와 설계 근거자료에서 직접 확인한 것만 사실로 쓰고 출처를 붙인다.
- 확인하지 못한 것은 사실로 쓰지 않고 spec.tmp.md의 `남은 것` 칸에 적는다.

## 실행

### 1. 불러오기

`<scratch 폴더>/scope.tmp.md`를 읽는다. 관련 ADR과 용어집이 있으면 함께 읽는다.

### 2. 코드 파악

scope.tmp.md의 `결정`이 닿는 영역과 가장 비슷한 기존 기능 후보를 좁힌 뒤 실제 코드로 확인한다.
진입점, 호출하는 쪽, 데이터가 지나가는 길까지 본다. scope.tmp.md의 `남은 것` 중 사실도 이때 확인한다.

### 3. 설계 근거자료 찾기

**설계 근거자료**(기획서, 시안, API 명세, DB 스키마 등)의 위치를 찾아 읽는다. 같은 대화에서 이미 읽은 것은 다시 읽지 않는다. 찾지 못하면 묻는다.

### 4. 명세 정하기

아래 칸으로 구현 명세를 정한다.

- **기존 기능과 다른 점**
  - 가장 비슷한 기존 기능과 시작 조건, 상태 변화, 권한, 데이터 형태, 에러 처리, 끝난 뒤 남는 것을 비교한다.
  - 다른 점마다 영향도(High, Low)를 붙인다.
  - 비슷한 기존 기능이 없는 새 프로젝트면 이 칸은 건너뛴다.
- **놓친 점**
  - 새 기능을 다음 질문에 대어 보고, 어떻게 처리할지 적는다. 해당 없으면 이유를 적는다.
    - 상태: 처리 중, 비었을 때, 실패했을 때 어떻게 되나
    - 권한: 누가 무엇을 할 수 있나
    - 데이터: 다루는 데이터의 모양이 바뀌나, 기존 데이터는 어떻게 되나
    - 계약: 이 변경에 기대는 다른 쪽이 있나
    - 성능: 느려지거나 자원과 비용이 늘어나나
    - 동시성: 같은 일이 동시에 여러 번 일어나면 어떻게 되나
    - 외부 연동: 기대는 바깥 서비스가 실패하면 어떻게 되나
    - 보안: 잘못되거나 나쁜 입력이 들어오면 어떻게 되나
    - 되돌리기: 문제가 생기면 어떻게 되돌리나
- **설계**
  - 바꿀 모듈, 인터페이스, 데이터 형태, 상태 위치를 정한다.
  - 기존 코드의 방식을 따른다. 새 프로젝트면 폴더 구조, 상태 관리, API 연동 방식, 공통 컴포넌트, 테스트 방식 같은 바탕 구조도 정한다.
  - `기존 기능과 다른 점`에 영향도 High가 있거나 기존 방식을 벗어나야 하면, 구조가 다른 방법을 두 개 이상 비교해 고르고 버린 대안과 고른 이유를 적는다.
  - 파일 위치와 함수 이름은 build가 정한다.
- **검증 방법**
  - 테스트가 있으면 가장 높은 테스트 지점 하나와 참고할 기존 테스트를 적는다.
  - 테스트가 없으면 확인 시나리오(무엇을 하면, 무엇이 보여야 하나)를 적는다.
- **이번에 하지 않는 것**
  - 명세를 쓰며 찾았지만 이번에 다루지 않기로 한 것을 적는다.
- **깨질 수 있는 기존 기능**
  - 이번 변경의 영향을 받는 기존 기능을 적는다.

### 5. 남은 결정 처리

코드와 설계 근거자료로 정할 수 없는 판단, scope.tmp.md의 `남은 것` 중 결정, 검증 방법의 테스트 지점을 사용자에게 묻는다.
scope와 같은 라운드 형식으로 묻는다. 답을 명세에 반영한다.

### 6. 기록 쓰기

`tmp.md 기록 규칙`대로 spec.tmp.md를 쓰고, `명세 정하기`와 `남은 결정 처리`에서 정한 명세를 `구현 명세`로 덧붙인다.

### 7. 최종 리뷰

리뷰는 **새 컨텍스트로 시작하는 subagent**에 맡긴다.
subagent의 결과는 고치거나 요약하지 않고 spec.tmp.md 끝에 `리뷰`로 붙인다.
합당한 결과는 명세에 즉각 반영한다.

- **기획 대조** (항상): 설계 근거자료 위치와 spec.tmp.md를 넘긴다. 명세가 설계 근거자료와 어긋나거나 빠진 것을 찾게 한다.
- **설계 반대 심문** (`기존 기능과 다른 점`에 영향도 High가 있거나 기존 방식을 벗어나는 설계일 때): spec.tmp.md와 그 설계 결정을 넘긴다. 설계를 반대 입장에서 공격하게 한다.

### 8. 종료

기록 경로와 구현 명세 요약을 간결하고 이해하기 쉽게 보고하고 멈춘다.
