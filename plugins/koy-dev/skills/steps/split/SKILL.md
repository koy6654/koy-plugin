# split

시작할 때 이 skill의 기준 폴더에서 세 단계 위(koy-dev plugin 루트)의 `reference/koy-config-usage.md`를 읽고 따른다.

명세를 **작업 단위**로 나눈다. 나누기만 한다. 구현은 사용자가 작업마다 새 세션에서 `/koy-dev:implement`로 진행한다.

## 1. 불러오기

`.claude/koy-config.md`와 인자로 받은 spec.md를 읽는다. 코드가 아직 낯설면 관련 영역을 훑는다. 먼저 구조를 고쳐두면 이후 작업이 쉬워지는 지점(선행 리팩터)이 있는지 본다.

## 2. 나누기

작업마다 다음을 지킨다.

- **세로로 자른다.** 한 작업이 필요한 모든 층(데이터, API 연동, 화면, 검증)을 좁게 관통한다. 한 층만 하는 작업은 만들지 않는다.
- **혼자서 확인할 수 있다.** 작업이 끝나면 그 작업만으로 동작을 보여주거나 검증할 수 있다.
- **새 세션 하나에 끝난다.** 작업 파일과 spec.md만 읽고 시작해도 일할 수 있다.
- **선행 리팩터가 있으면 맨 앞에 둔다.**

작업마다 **선행 작업**(이 작업보다 먼저 끝나야 하는 작업)을 정한다. 선행 작업이 없으면 바로 시작할 수 있다.

예외: 이름 바꾸기처럼 기계적인 변경 하나가 코드 전체에 퍼지는 경우는 세로로 자를 수 없다. 이때는 새 형태를 옆에 추가 → 호출부를 묶음 단위로 옮김 → 옛 형태 삭제 순서로 나눈다.

## 3. 보여주기

나눈 결과를 번호 목록으로 보여준다.

```
01. <제목>
    선행: 없음
    결과: <이 작업이 끝나면 처음부터 끝까지 동작하는 것>
02. ...
```

보여준 뒤 기다리지 않고 4단계로 간다. 작업 파일을 쓴 뒤 사용자가 크기·선행 관계·합치기·나누기를 고치라고 하면 파일을 고친다.

## 4. 작업 파일 쓰기

`<산출물 위치>/<slug>/issues/<NN>-<작업-slug>.md`에 작업 하나당 파일 하나를 쓴다. 선행 작업이 앞에 오도록 01부터 번호를 매긴다. 파일 경로와 코드 조각은 넣지 않는다.

```markdown
# <NN>: <작업 제목>

**만들 것:** <사용자 관점에서 이 작업이 동작하게 만드는 것>

**선행:** <번호와 제목 | 없음 (바로 시작 가능)>

**상태:** 대기

## 완료 기준
- [ ] <확인 가능한 기준>

## 참고
명세: `<산출물 위치>/<slug>/spec.md`
```

「이슈 트래커」가 Jira·GitHub처럼 실제 트래커여도, 이 단계에서는 로컬 파일만 쓴다. 트래커에 올릴지는 사용자에게 묻고, 올린다면 그 규칙을 따른다.

## 5. 종료

흐름 skill(`/koy-dev:feature`, `/koy-dev:build`, `/koy-dev:bugfix`) 안에서 실행 중이면, 결과를 보고하고 흐름 skill의 다음 지시로 돌아간다. 아래 안내는 이 skill을 단독으로 실행했을 때만 따른다.

작업 파일 목록을 보여주고 멈춘다. 진행 방법을 안내한다.

```
작업마다 새 세션에서:
/koy-dev:implement <산출물 위치>/<slug>/issues/01-<작업-slug>.md
→ /koy-dev:ready
→ 커밋 후, 작업 파일의 상태를 "완료"로 바꾼다
선행 작업이 모두 "완료"인 파일부터 진행한다.
```
