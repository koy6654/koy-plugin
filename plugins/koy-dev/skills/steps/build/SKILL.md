# build

구현 전용 step. **승인된 계획에 있는 것만** 코드로 만들고, **실제 동작으로** 증명한다. 커밋은 하지 않는다.

## 원칙

- `${CLAUDE_PLUGIN_ROOT}/skills/RULES.md`를 읽고 따른다. 같은 대화에서 이미 읽었으면 건너뛴다.

## 실행

### 0. 규칙 읽기

저장소의 `CLAUDE.md`와 이번 작업에 해당하는 규칙·컨벤션 문서를 직접 다시 읽는다. 기억이나 요약에 기대지 않는다.

### 1. 준비

1. 아래 입력을 우선순위에 맞게 모두 읽는다. 내용이 서로 다르면 우선순위가 위에 있는 것을 따른다. 입력이 없거나, 다 읽고도 무엇을 어떻게 만들지 알 수 없으면 묻는다.
   - 입력으로 주어진 ticket 파일
   - scratch 폴더의 spec.tmp.md
   - scratch 폴더의 scope.tmp.md
   - scratch 폴더의 debug.tmp.md
   - 입력으로 주어진 요청 설명
2. **ticket이 없으면 만든다.** (build 기록이 여러 곳에 흩어지지 않고 ticket 파일 한 곳에 모이도록) split의 ticket 양식에 맞춘 ticket 하나를 `<scratch 폴더>/tickets/`에 만든다.
3. 바꿀 코드와 그 호출부를 확인한다. 비슷한 기존 코드가 어떻게 되어 있는지 본다.
4. **도메인 모델을 먼저 정한다.**
   - 도메인 모델은 코드 안에서 다루는 대상과 그 상태를 표현하는 구조다.
   - 입력에 정해져 있으면 따른다.
   - 없으면 코드를 쓰기 전에, 있을 수 없는 상태가 생기지 않고 같은 판단이 여러 곳에 흩어지지 않는 구조로 정한다.
5. **테스트를 먼저 실행하고 결과를 기록해둔다.**
   - 코드 수정 후 실패가 이번 변경 때문인지 가리는 데 사용한다.
   - 검증 명령어와 실제 동작 확인 방법을 CLAUDE.md, CI 설정, package manifest 등에서 찾아 ticket 파일의 `기준 상태`에 적는다. 없으면 묻는다.
   - 검증 명령어를 실행하고, 원래부터 실패하던 항목을 ticket 파일의 `기준 상태`에 적는다.
   - build를 다시 실행해도 ticket 파일의 `기준 상태`는 새로 적지 않는다.

### 2. 계획과 승인

1단계에서 읽은 입력으로 아래 변경 계획을 세우고 승인받는다. 승인 전에는 코드를 바꾸지 않는다.

```markdown
## 변경 계획

### 바꿀 파일

<새로 만들거나 고칠 파일, 바꿀 내용, 주요 함수>

### 도메인 모델

<1단계에서 정한 구조>

### 예상 위험

<깨질 수 있는 곳과 막는 방법>

### 실행 순서

<확인할 수 있는 작은 단위로 나눈 순서. 단위마다 무엇으로 확인하는지>

### 검증 방법

<입력에 정해진 검증 방법. 없으면 이번에 정한 확인 시나리오>
```

### 3. 구현

아래 **최소 구현 순서**를 따른다. 위에서 해결되면 아래로 내려가지 않는다.

1. 프로젝트에 이미 있는 코드로 되는지 검토한다. 기존 함수, 공통 모듈, 비슷한 기능의 구현 등을 본다.
2. 쓰고 있는 프레임워크나 플랫폼이 해주는지 검토한다.
3. 이미 설치된 의존성으로 되는지 검토한다.
4. 그래도 안 되면 새로 작성한다. 새 패키지가 필요하면 따로 승인받는다.

구현하는 동안 다음을 지킨다.

- **작은 단위로 진행한다.** 계획의 실행 순서대로 한 단위를 바꾸고, 확인하고, 통과하면 다음으로 간다.
- **spec.tmp.md나 debug.tmp.md에 정해진 테스트를 먼저 쓴다.** 그 테스트가 실패하는 것을 본 뒤 구현한다.
- **줄이지 않는다.** 입력 검증, 권한 검증, 에러 처리, spec.tmp.md나 debug.tmp.md에 정해진 테스트, CLAUDE.md가 명시한 규칙은 최소 구현 순서를 따르더라도 줄이지 않는다.
- **명세와 다르게 가야 하면 멈추고 보고한다.** 승인된 계획이나 명세대로 할 수 없으면 다르게 만들지 않고, 무엇이 왜 안 되는지 보고한다.

### 4. 검증

verify step의 `검증 명령어`와 `실제 동작 확인`대로 검증한다. 새로 생긴 실패는 고친다.

### 5. 과잉 구현 점검

이번에 바꾼 것만 다시 보고 다음을 찾는다.

- **쓰이지 않는 것**: 만들었지만 아무 곳에서도 쓰지 않는 것
- **이미 있는 것을 다시 만든 것**: 이미 있는 것으로 될 일을 새로 만든 것
- **지금 필요 없는 대비**: 지금 요구에 없는데 나중을 위해 미리 만든 것. 외부 패키지를 감싸거나 저장소 규칙이 요구하는 것은 빼고 본다.
- **요청 범위를 넘은 것**: 승인된 계획에 없는 변경

발견한 것은 고치지 않고 `과잉 구현 후보`로 모은다. 사용자가 반영을 요청하면 반영하고 4단계를 다시 돈다.

### 6. 기록 쓰기

`tmp.md 기록 규칙`대로 ticket 파일에 build 기록을 마저 쓰고, build 단계에서 한 일과 결과를 단계마다 덧붙인다.

### 7. 종료

ticket 파일 경로와 build 기록을 간결하고 이해하기 쉽게 보고하고 멈춘다.
