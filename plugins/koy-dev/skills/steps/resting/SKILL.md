# resting

grill 다음의 검증 step. 정한 요구사항을 실제 코드와 원천에 맞대어 **빈틈**과 **놓친 점**을 찾고, implement가 따라갈 **resting.tmp.md**를 만든다. 분석만 한다. 쓰기는 `<scratch 폴더>` 안에서만 한다.

## 원칙

`${CLAUDE_PLUGIN_ROOT}/skills/RULES.md`를 읽고 따른다. 같은 대화에서 이미 읽었으면 건너뛴다.

## 근거 원칙

기억, 대화 내용, 과거 ADR, grill에서 본 내용은 전부 **힌트**다. 사실로 쓰려면 지금의 코드나 원천을 직접 확인한다. 모든 주장은 출처와 함께 쓴다.

```
<확인된 사실>. 출처: <파일:심볼 | 문서 위치 | 실행한 명령과 결과>
```

출처를 붙일 수 없는 주장은 「남은 불확실성」에 둔다.

## 실행

### 1. 불러오기

`<scratch 폴더>/grill.tmp.md`를 읽는다. 관련 ADR과 용어집이 있으면 함께 읽는다.

### 2. 열린 질문 해소

grill.tmp.md의 `남은 것`을 하나씩 처리한다.

```markdown
### 열린 질문: <질문>
- 결론:
- 확인 방법:
- 출처:
- 남은 불확실성:
```

**완료 기준**: 모든 열린 질문에 결론이나 「남은 불확실성」이 적혀 있다.

### 3. 대조

요구사항이 기대는 **원천**을 찾는다: 시안(Figma 등), API 명세, DB 스키마, 정책서, 기존 ADR. 연결된 저장소 skill이 있으면 그것으로 가져온다. 원천마다 요구사항과 맞대어 본다. 어긋나는 점, 요구사항에 없는데 원천에 있는 것, 원천에 없는데 요구사항에 있는 것을 적는다. 있어야 할 것 같은데 찾지 못한 원천은 묻는다.

**완료 기준**: 찾은 모든 원천에 대조 결과가 적혀 있고, 찾지 못한 원천은 그 사실이 적혀 있다.

### 4. 비슷한 기능과 비교

"기존 기능 X와 같겠지"는 가설이다. 가장 비슷한 기존 기능을 찾아 새 요구사항과 나란히 놓고 비교한다: 무엇이 시작시키나, 상태가 어떻게 바뀌나, 권한, 에러 처리, 데이터 형태, 완료 후 무엇이 남나.

차이를 영향도로 나눈다.

```markdown
## 빈틈
### High
### Medium
### Low
```

### 5. 놓친 점

아래 기본 항목과, 저장소 문서에 체크리스트가 있으면 그 항목까지 **모두** 답한다. 해당 없음도 이유와 함께 적는다.

- 상태: 로딩, 빈 상태, 에러, 권한 없음, 부분 성공
- 권한·소유권: 누가 무엇을 볼 수 있고 바꿀 수 있나
- 데이터: 형태 변경, 마이그레이션, 기존 데이터 호환, 삭제·복구
- 계약: API·이벤트·화면 사이의 약속이 바뀌면 영향받는 쪽
- 성능: 목록 크기, 반복 호출, 페이지 나누기
- 동시성: 중복 요청, 경쟁 상태, 멱등성
- 외부 연동: 실패, 재시도, 시간 초과
- 되돌리기: 배포 후 문제가 생기면 어떻게 되돌리나

체크리스트 밖에서 구현에 영향을 줄 것을 찾았다면 추가로 적는다.

### 6. 검증 방법 합의

implement가 결과를 어떻게 증명할지 정한다.

- 테스트가 있는 프로젝트: 동작을 밖에서 관찰할 수 있는 지점 중 **가장 높은 곳 하나**를 테스트 지점으로 고른다. 이미 테스트가 걸린 지점이 있으면 그것을 쓴다. 같은 지점의 기존 테스트 파일을 참고 예시로 적는다.
- 테스트가 없거나 마땅한 지점이 없는 경우: 만든 기능을 직접 확인하는 방법(화면, 실행, 호출)을 찾아 **관찰할 시나리오**를 적는다 (무엇을 하고, 무엇이 보여야 통과인가). 마땅한 테스트 지점이 없다는 사실도 빈틈에 올린다.

정한 검증 방법은 resting.tmp.md에 적고 보고에 포함한다. 사용자는 implement의 변경 계획 승인에서 이를 다시 본다.

### 7. 남은 결정

코드와 원천으로 정할 수 없는 제품·비즈니스 판단이 남았으면 grill과 같은 라운드 형식으로 묻는다. 코드로 답이 나오는 것은 코드로 답한다.

### 8. resting.tmp.md 쓰기

`<scratch 폴더>/resting.tmp.md`를 쓴다. 파일 경로와 코드 조각은 넣지 않는다. 금방 낡는다.

```markdown

## 1. 요약
## 2. 확인된 맥락
<근거 원칙 형식의 사실 목록>
## 3. 열린 질문 결과
## 4. 대조 결과
## 5. 빈틈
## 6. 놓친 점
## 7. 구현 결정
<바꿀 모듈과 그 인터페이스, 데이터 형태, 상태 모델>
## 8. 검증 방법
<합의된 테스트 지점 또는 관찰 시나리오>
## 9. 범위 밖
## 10. 회귀 위험
## 11. 남은 불확실성
## CLAUDE.md 후보
<앞으로 계속 지킬 규칙. 없으면 "없음". 반영은 close가 한다>
## 물어본 것
<RULES.md `tmp.md 기록 규칙`의 `물어본 것` 형식. 없으면 "없음">
```

### 9. 종료

resting.tmp.md 경로와 주요 발견을 보고하고 멈춘다.
