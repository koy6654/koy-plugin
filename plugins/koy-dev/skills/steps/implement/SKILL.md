# implement

승인받은 계획대로, **필요한 만큼만** 만들고, **실제 동작으로** 증명한다. 커밋은 하지 않는다.

## 시작 전 실행

`${CLAUDE_PLUGIN_ROOT}/skills/RULES.md`를 읽고 따른다. 같은 대화에서 이미 읽었으면 건너뛴다.

## 0. 규칙 다시 읽기

`CLAUDE.md`와 그것이 가리키는 규칙 문서를 실제로 다시 읽는다. 이번 scratch에 걸리는 규칙을 한 줄씩 **자기 말로** 다시 적어 사용자에게 보여준다. 본문에서 찾지 못한 규칙은 "본문에 없음"이라고 적는다.

## 1. 준비

1. 입력을 읽는다. 이 세션의 scratch이거나 scratch 폴더 경로를 받았으면 `<scratch 폴더>`의 resting.tmp.md(없으면 grill.tmp.md)를, issue 파일이면 그 파일과 resting.tmp.md를 읽고 「구현 결정」「검증 방법」「범위 밖」을 따른다. 요청 설명뿐이면 범위와 완료 기준을 먼저 한 줄씩 적는다.
2. 바꿀 코드와 그 호출부를 확인한다. 비슷한 기존 코드가 어떻게 되어 있는지 본다.
3. **데이터 형태를 먼저 정한다.** 상태가 있으면 흩어진 boolean 대신 상태 기계나 판별 유니온(discriminated union)으로, 분기가 여러 파일에 퍼질 것 같으면 조회 테이블로 표현한다. 지금 형태가 이미 단순하고 커질 일이 없으면 그대로 둔다.
4. **기준 상태를 기록한다.** **검증 명령어**(CLAUDE.md, `package.json` scripts, CI 설정)와 **실제 동작 확인 방법**을 저장소에서 찾고, 없으면 묻는다. 고치기 전에 검증 명령어를 한 번 돌리고, 원래부터 실패하던 항목과 커밋되지 않은 남의 파일을 기록(`<scratch 폴더>/implement.tmp.md`, issue 파일을 받았으면 `implement-<NN>.tmp.md`)의 「기준 상태」에 먼저 적어둔다. 요청 설명만 받았으면 scratch 이름을 기능을 나타내는 짧은 영문 kebab-case로 정하고 사용자에게 보여준다. 다시 실행할 때 「기준 상태」는 처음 기록을 유지한다.

## 2. 계획과 승인

```markdown
## 변경 계획
### 새 파일
### 수정 파일
### 데이터 형태
### 예상 위험
### 실행 순서
<확인 가능한 작은 단위들. 단위마다 무엇으로 확인하는지>
### 검증 방법
<resting.tmp.md의 검증 방법 또는 이번에 정한 관찰 시나리오>
```

AskUserQuestion으로 승인받는다: **예, 진행** / **수정 후 진행** / **취소**. 승인 전에는 코드를 바꾸지 않는다.

## 3. 구현

**최소 구현 순서**를 따른다. 위 칸에서 해결되면 아래 칸으로 내려가지 않는다.

1. 이미 있나 (프로젝트의 기존 헬퍼, 공통 컴포넌트, 비슷한 기능의 패턴)
2. 프레임워크나 플랫폼이 해주나
3. 설치된 의존성으로 되나
4. 새로 작성한다 (새 패키지는 따로 승인받는다)

다음은 짧게 줄이지 않는다: 입력 검증, 권한 검증, 에러 처리, 합의된 테스트, CLAUDE.md가 명시한 규칙.

**작은 단위로 진행한다.** 계획의 실행 순서대로 한 단위를 바꾸고, 그 단위를 확인하고, 통과하면 다음으로 간다. 합의된 테스트 지점이 있으면 그 테스트를 먼저 써서 실패하는 것을 본 뒤 구현한다.

## 4. 검증

1. 준비에서 찾은 검증 명령어를 전부 돌린다. 「기준 상태」에 있던 실패는 "기존"으로, 새로 생긴 실패는 이번 변경이 만든 것으로 구분한다. 새 실패는 고친다.
2. **실제 동작으로 증명한다.** 준비에서 찾은 실제 동작 확인 방법과 계획의 검증 방법에 따라 만든 것을 직접 관찰하고, 무엇을 했고 무엇을 봤는지 그대로 남긴다. 빌드 통과와 자기 판단은 증거로 치지 않는다. 확인 과정을 스크립트로 만들 수 있으면 스크립트로 만들고 실행 결과를 남긴다.
3. 직접 관찰할 수 없는 경우에는 그 이유와 사용자가 확인할 방법을 적는다. "확인 못 함"은 통과가 아니다.

## 5. 과잉 구현 점검

이번에 바꾼 코드만 다시 보고 다음을 찾는다.

- 한 곳에서만 쓰는 추상화, 쓰이지 않는 옵션이나 확장 지점
- 프레임워크나 기존 코드가 이미 해주는 것을 다시 짠 곳
- 요청 범위를 넘은 변경

발견한 것은 고치지 않고 기록의 「과잉 구현 후보」에 적는다. 사용자가 반영을 요청하면 반영하고 4번을 다시 돈다.

## 6. 종료

기록을 완성한다.

```markdown
# <기능 이름> 구현

## 기준 상태
<구현 전 검증 결과: 기존 실패, 남의 미커밋 파일>
## 바꾼 파일
## 검증 결과
<명령어 결과 (기존 실패와 새 실패 구분)>
## 실제 동작 확인
<무엇을 했고 무엇을 봤나. 확인 못 했으면 이유와 사용자가 확인할 방법>
## 과잉 구현 후보
## 남은 일
## 물어본 것
<RULES.md 「scratch 기록 규칙」의 「물어본 것」 형식. 없으면 "없음">
```
